# v0.5.0 — Webhook / HTTP POST / Syslog alerts + send test

Release notes for version **0.5.0** (minor: new alert channels and a send test). See also
[`CHANGELOG.md`](../../CHANGELOG.md) and the design in
[`doc/00 §11`](../00-Architecture_and_Specification.md).

## Added

### Three new alert channels

Besides `sound`/`popup`/`telegram`/`log`, each alert now has a stable **`id`** and the new channels use a
nested **`options:`** block (the four existing types keep their flat fields — **no config migration**):

| `type` | What it does |
|---|---|
| `webhook` | `POST`/`PUT`/`PATCH` JSON to a webhook URL (MS Teams **Workflows**, Slack, Discord, Mattermost…) |
| `http_post` | JSON POST to a **host/IP + port** (or a full URL); for internal APIs |
| `syslog` | sends an **informational** syslog message to host/port (`udp` default, `tcp` optional) — no image |

```yaml
profiles:
  default:
    alerts:
      - type: webhook                    # Teams Workflows / Slack / Discord / Mattermost…
        id: teams
        severity_min: 2
        cooldown_s: 60
        options:
          url_env: TEAMS_WEBHOOK         # secret stays out of the YAML
          method: POST
          payload:                       # basic template (mapping)
            text: "Change on ${target}: ${strategy} score=${score} sev=${severity}"
          timeout_s: 5

      - type: http_post
        id: erp-api
        severity_min: 3
        options:
          scheme: http
          host: 10.0.0.20
          port: 8080
          path: /alerta
          headers: { Authorization: "Bearer ${env:ERP_TOKEN}" }
          payload: { evento: "mudanca", alvo: "${target}" }

      - type: syslog
        id: siem
        severity_min: 1
        cooldown_s: 0
        options:
          host: 10.0.0.9
          port: 514
          protocol: udp
          facility: local0
          app_name: screen-diff-watcher
          payload_raw: "${timestamp} ${target} ${strategy} score=${score} sev=${severity}"
```

### Payload template

- `payload:` (mapping) is the **basic template**: `${field}` is substituted **only in string values**;
  `payload_raw:` (string) sends a non-object body.
- Using both `payload` and `payload_raw` is a config error (`config.alert_payload_conflict`).
- Placeholders: `message`, `strategy`, `score`, `threshold`, `severity`, `target`, `timestamp`,
  `window_handle`, `changed`, `roi`, and **`env:VAR`** (read from the environment **at send time**).
  `$$` escapes `$`; `{`/`}` stay literal, so the body can be JSON. An unknown placeholder is a config
  error (`config.alert_unknown_placeholder`).

### Secrets and TLS

- The URL is literal (`url`) **or** from the environment (`url_env: VAR`); any string in `headers`/
  `payload` accepts `${env:VAR}`.
- Error messages and logs **never** expose the resolved URL (`scheme://host/…`) or the `${env:VAR}`
  values.
- `verify_tls: true|false` (default `true`) for internal endpoints with a self-signed certificate; with
  `false`, a warning is logged **on every send**.

### Stable `id` and cooldown fix

Every alert now has an **`id`** (default `type`; `type#n` when repeated in the same profile). The `id`
is the **cooldown key**, so two webhooks no longer share the cooldown. A duplicated explicit `id` is a
config error (`config.alert_duplicate_id`).

### Send test

- **CLI**: `test-alert --list` (id/type/state/destination) and `test-alert --only <id>` (one destination;
  the send uses **text mode** when there is no ROI). Without flags, the behavior is the same as before
  (respects `enabled`, via `AlertChain`).
- **GUI**: the **Test alert…** button opens a dialog with the configured alerts; the send runs on a
  worker thread (so a 5 s timeout never freezes the UI) and falls back to text mode when there is no
  ROI.

## Changed

- **Unknown alert `type` is now a config error** (`config.alert_unknown_type`) instead of a silent
  warning — a "mute" channel no longer goes unnoticed. The `run`/`test-*` CLI now warns when an
  existing config is invalid and it falls back to the default alerts.
- **Cooldown identity changed**: the key is now the alert `id` (default `type`, `type#n` when
  repeated), not the notifier class name. A profile that lists **two alerts of the same type** (e.g.
  two `telegram` entries) now fires **both** per cooldown window; previously they shared one key and
  only the first fired. This is intentional (it is the same fix that stops two webhooks from sharing
  a cooldown).
- `AlertChain` uses `getattr(notifier, "uid", notifier.name)` as the cooldown key (compatible with
  notifiers built outside `build_notifier`).

## Limitations

- No image/ROI on the new channels (the attached print stays exclusive to Telegram).
- Syslog over **UDP does not confirm delivery** — prefer `tcp` when delivery must be confirmed.
- MS Teams **Incoming Webhooks are being retired** (deadline **2026-03-31**, shutdown **2026-05**):
  use the **Workflows** webhook URL; the configurable payload avoids locking into the legacy format.
- No guaranteed delivery/queue: the `AlertChain` cooldown + backoff still applies.

## Config error codes (new)

`config.alert_unknown_type`, `config.alert_options_not_mapping`, `config.alert_missing_url`,
`config.alert_missing_host`, `config.alert_invalid_url`, `config.alert_invalid_port`,
`config.alert_invalid_protocol`, `config.alert_invalid_facility`, `config.alert_invalid_method`,
`config.alert_payload_conflict`, `config.alert_unknown_placeholder`,
`config.alert_invalid_severity_map`, `config.alert_duplicate_id`, plus the runtime
`alert.http_status`, `alert.http_unreachable` and `alert.syslog_unavailable`.

## Upgrading

Nothing to migrate: existing YAML keeps working (flat fields of `sound`/`popup`/`telegram`/`log` are
unchanged). Add the new channels with an `options:` block and, if you want to select them by name, set an
explicit `id`.
