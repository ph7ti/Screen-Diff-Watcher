# v0.5.0 — Alertas Webhook / HTTP POST / Syslog + teste de envio

Notas da versão **0.5.0** (minor: novos canais de alerta e teste de envio). Veja também o
[`CHANGELOG.md`](../../CHANGELOG.md) e o design no
[`doc/00 §11`](../00-Documento_de_Arquitetura_e_Especificação.md).

## Adicionado

### Três canais de alerta novos

Além de `sound`/`popup`/`telegram`/`log`, cada alerta agora tem um **`id`** estável e os canais novos
usam um bloco aninhado **`options:`** (os quatro tipos atuais mantêm os campos planos — **sem migração**):

| `type` | O que faz |
|---|---|
| `webhook` | `POST`/`PUT`/`PATCH` JSON para uma URL de webhook (MS Teams **Workflows**, Slack, Discord, Mattermost…) |
| `http_post` | POST JSON para **host/IP + porta** (ou URL completa); para APIs internas |
| `syslog` | envia mensagem **informational** para host/porta (`udp` default, `tcp` opcional) — sem imagem |

```yaml
profiles:
  default:
    alerts:
      - type: webhook                    # Teams Workflows / Slack / Discord / Mattermost…
        id: teams
        severity_min: 2
        cooldown_s: 60
        options:
          url_env: TEAMS_WEBHOOK         # segredo fora do YAML
          method: POST
          payload:                       # modelo básico (mapping)
            text: "Mudança em ${target}: ${strategy} score=${score} sev=${severity}"
          timeout_s: 5

      - type: http_post
        id: erp-api
        severity_min: 3
        options:
          scheme: http
          host: 10.0.0.20
          port: 8080
          path: /alerta
          headers: { Authorization: "Bearer ${env:ERP_TOKEN}" }
          payload: { evento: "mudanca", alvo: "${target}" }

      - type: syslog
        id: siem
        severity_min: 1
        cooldown_s: 0
        options:
          host: 10.0.0.9
          port: 514
          protocol: udp
          facility: local0
          app_name: screen-diff-watcher
          payload_raw: "${timestamp} ${target} ${strategy} score=${score} sev=${severity}"
```

### Modelo de payload

- `payload:` (mapping) é o **modelo básico**: `${campo}` é substituído **só em valores string**;
  `payload_raw:` (string) envia um corpo que não é objeto.
- Usar `payload` **e** `payload_raw` é erro de config (`config.alert_payload_conflict`).
- Placeholders: `message`, `strategy`, `score`, `threshold`, `severity`, `target`, `timestamp`,
  `window_handle`, `changed`, `roi` e **`env:VAR`** (lido do ambiente **no envio**). `$$` escapa `$`;
  `{`/`}` ficam literais, então o corpo pode ser JSON. Placeholder desconhecido é erro de config
  (`config.alert_unknown_placeholder`).

### Segredos e TLS

- A URL é literal (`url`) **ou** do ambiente (`url_env: VAR`); qualquer string de `headers`/`payload`
  aceita `${env:VAR}`.
- Erros e logs **nunca** expõem a URL resolvida (`scheme://host/…`) nem os valores de `${env:VAR}`.
- `verify_tls: true|false` (default `true`) para endpoints internos com certificado autoassinado; com
  `false`, um aviso é registrado **a cada envio**.

### `id` estável e correção do cooldown

Cada alerta agora tem um **`id`** (default `type`; `type#n` quando repetido no mesmo perfil). O `id` é a
**chave de cooldown**, então dois webhooks não compartilham mais o cooldown. `id` explícito duplicado é
erro de config (`config.alert_duplicate_id`).

### Teste de envio

- **CLI**: `test-alert --list` (id/tipo/estado/destino) e `test-alert --only <id>` (um destino; o envio
  usa **modo texto** quando não há ROI). Sem flags, o comportamento é o mesmo de antes (respeita
  `enabled`, via `AlertChain`).
- **GUI**: o botão **Testar alerta…** abre um diálogo com os alertas configurados; o envio roda em
  **thread de trabalho** (um timeout de 5 s não congela a UI) e cai para modo texto quando não há ROI.

## Mudado

- **Tipo de alerta desconhecido passa a ser erro de config** (`config.alert_unknown_type`) em vez de
  aviso silencioso — um canal "mudo" deixa de passar batido. O CLI (`run`/`test-*`) agora avisa quando
  um config existente está inválido e cai para os alertas padrão.
- **Identidade de cooldown mudou**: a chave agora é o `id` do alerta (default `type`, `type#n` quando
  repetido), não o nome da classe do notificador. Um perfil que lista **dois alertas do mesmo tipo**
  (ex.: dois `telegram`) agora dispara **os dois** por janela de cooldown; antes eles compartilhavam a
  chave e só o primeiro disparava. É intencional (é a mesma correção que impede dois webhooks de
  compartilhar o cooldown).
- O `AlertChain` usa `getattr(notifier, "uid", notifier.name)` como chave de cooldown (compatível com
  notificadores construídos fora do `build_notifier`).

## Limitações

- Sem imagem/ROI nos canais novos (o print anexado continua exclusivo do Telegram).
- Syslog por **UDP não confirma entrega** — prefira `tcp` quando a entrega precisa ser confirmada.
- Os **Incoming Webhooks** do MS Teams estão sendo descontinuados (prazo **31/03/2026**, desligamento
  **maio/2026**): use a URL do **Workflows**; o payload configurável evita travar no formato legado.
- Sem entrega garantida/fila: continua valendo o cooldown + backoff do `AlertChain`.

## Códigos de erro novos

`config.alert_unknown_type`, `config.alert_options_not_mapping`, `config.alert_missing_url`,
`config.alert_missing_host`, `config.alert_invalid_url`, `config.alert_invalid_port`,
`config.alert_invalid_protocol`, `config.alert_invalid_facility`, `config.alert_invalid_method`,
`config.alert_payload_conflict`, `config.alert_unknown_placeholder`,
`config.alert_invalid_severity_map`, `config.alert_duplicate_id`,
além dos de runtime `alert.http_status`, `alert.http_unreachable` e `alert.syslog_unavailable`.

## Atualizando

Nada a migrar: o YAML existente continua funcionando (os campos planos de
`sound`/`popup`/`telegram`/`log` não mudaram). Adicione os canais novos com um bloco `options:` e, para
selecioná-los pelo nome, informe um `id` explícito.
